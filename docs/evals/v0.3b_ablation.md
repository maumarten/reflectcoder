# v0.3b ablation — reflective vs reflective-memory (cold vs warm)

v0.3b adds a persistent failure memory to the reflective agent. On each
proposer call, the agent retrieves the top-k most similar prior failures
(by cosine similarity over sentence-transformer embeddings of
`problem + stderr`) and injects them as hints. On each failed attempt that
produces a reflection, the agent writes the record back to the SQLite store.

The methodology is a two-phase repeat run on the same fixture set with the
same model (`llama-3.3-70b-versatile`):

- **Cold run**: `--reset-memory`. Store is empty at start. Behaviour should
  be indistinguishable from the plain `reflective` agent because there is
  nothing to retrieve.
- **Warm run**: the store from the cold run is retained. The agent can now
  retrieve prior failures from other tasks when proposing. This is where
  memory should start paying for itself — specifically on `bug_008`, which
  exhausted the loop in v0.3a.

## Warm run (store populated)

**Status:** deferred. The warm run was blocked by the Groq free-tier daily
token cap (100k TPD on `llama-3.3-70b-versatile`) — the cold run consumed
the remaining budget for the day, and every warm-run proposer call hit 429.
The `reflective-memory` circuit breaker correctly detected the LLM-error
regime and aborted cleanly; no partial-run numbers are published because
they would only measure rate-limit behaviour, not the memory layer.

Reproduction command once the TPD resets:

```bash
# do NOT pass --reset-memory; we want the 4 cold-run failures retained
python -m reflectcoder eval --agent reflective-memory --max-iter 3
```

The warm headline + per-fixture table will be filled in once the quota
resets. The specific questions this ablation is meant to answer:

1. **Does bug_008 cross the pass line?** It failed at iter=3 in the cold
   run. The warm run gives it 2 prior failure reflections on the same task
   (plus the path-normalize reflections) at proposer-time. If iter-0 of the
   warm run incorporates those hints and produces a correct state machine,
   that's the first clean demonstration of memory value in this repo.
2. **Does bug_007 reach pass in fewer iterations?** Cold took 3. Warm has
   the cold reflections retrievable — though filtered to cross-task only
   (retrieval excludes the current task's own rows to avoid self-
   reinforcement), so bug_007's gain from its own prior failures is zero.
   The only cross-pollination available on warm is bug_008 ↔ bug_007 and
   vice versa — we should not expect a huge bug_007 delta.

## Cost calculus

Memory adds three costs:

- Embedding time: one `SentenceTransformer.encode` call per proposer
  invocation (~50ms on CPU for 384-d MiniLM).
- Prompt token overhead: the "similar prior failures" block is capped at
  ~3 records, each one-lined to <400 chars, so ~1.5k chars / ~400 tokens
  added per warm proposer call in the worst case.
- Storage: SQLite file, ~5KB per failure row (most of it the embedding
  blob).

All negligible against the 12k+ tokens of a loop run. The economic question
is purely whether the retrieval cuts iterations enough to offset the
per-call prompt tax.

## Methodology honesty

Two caveats worth stating in public:

1. The fixture set is still small (n=8). The cold-vs-warm comparison is an
   existence proof at best; claims like "memory cuts iterations by X%"
   need a larger and more diverse fixture corpus before they're defensible.
2. Retrieval excludes the current task's own rows, so within a single
   cold-then-warm pair of runs the cross-pollination available is limited
   to the 2 hard tasks swapping hints. A more realistic ablation would run
   warm against a larger store built up from many unrelated prior tasks —
   which is what v0.4+ will start to enable once the SWE-bench Lite subset
   lands.

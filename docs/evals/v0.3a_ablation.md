# v0.3a ablation — stub vs reflective on 8 fixtures

Both agents use the same model (`llama-3.3-70b-versatile`) and the same
proposer system prompt. The only difference is the control flow: `stub` makes
one LLM call and returns; `reflective` runs a plan → patch → test → reflect →
retry loop with `max_iter=3` and a circuit breaker.

v0.3a adds three harder fixtures targeting categories where one-shot is more
likely to miss: specific-message error handling, under-specified edge cases,
and stateful parsing.

## Headline

| Agent        | Fixtures | Pass | Pass rate | Total tokens | Wall clock |
|--------------|----------|------|-----------|--------------|------------|
| stub         | 8        | 6    | 75.0%     | 5250         | 51.3s      |
| reflective   | 8        | 7    | **87.5%** | 12618        | 56.6s      |

**Delta:** +1 fixture passed (`bug_007_path_normalize`) via genuine iteration
at ~2.4× token cost.

## Where the loop actually fired

For the first time in this repo's history, the reflective loop's
retry-after-reflection behaviour made a clean, auditable difference in the
published ablation: `bug_007_path_normalize` failed on iteration 0, the
reflector diagnosed the specific edge cases that were still wrong (empty input
→ `.`, root-only parent traversal, etc.), and iteration 1 passed. This is
exactly the shape of recovery the loop was designed for — miss a subset of
cases, read the test output, patch the gap.

On `bug_008_csv_parser_quoted`, the loop exhausted its 3-iteration budget
without passing. That is also informative: reflection alone isn't enough for
this level of state-machine specification drift. v0.3b's failure memory is
meant to target exactly this — so that a future run on a related parsing task
can retrieve the failed attempts from bug_008 and avoid repeating them.

## Why the harder fixtures were chosen

Each new fixture targets a category where the one-shot model tends to miss:

- **`bug_006_rpn_calculator`** — specific error type + exact error message
  requirements. The one-shot model tends to raise `IndexError` rather than
  `ValueError("insufficient operands")`. Turned out to be inside the model's
  capability one-shot, but stresses the proposer's attention to spec.
- **`bug_007_path_normalize`** — under-specified edge cases (empty input,
  `..` at root, trailing slash rules). The shape of the correct behaviour is
  only knowable by reading the tests. This is where the reflective loop
  earned its keep.
- **`bug_008_csv_parser_quoted`** — RFC 4180 quoting rules implemented as a
  state machine. Breaks `split(",")` based naïve implementations hard. Hard
  enough that the current reflective loop still can't solve it in 3
  iterations.

## Cost per passed task

| Agent        | Tokens / passed task |
|--------------|----------------------|
| stub         | 875                  |
| reflective   | 1803                 |

Reflective is now more expensive per passed task than stub on this set —
because the failed `bug_008` burns the full 3-iteration budget, and the other
reflective passes ran at iter=1 (paying the same cost as stub plus a small
prompt-overhead tax). This is the *expected* shape: the loop is an insurance
mechanism that costs nothing extra when the one-shot succeeds, and costs
multiple iterations when it doesn't. The economic question for v0.3b is
whether failure memory can cut the cost of recovery on the long tail.

## What this sets up for v0.3b

Two specific signals for the memory layer to target:

1. **`bug_008`'s failed attempts should be useful on re-runs.** If the
   reflector's iteration-2 or iteration-3 reflection (once embedded and
   retrieved) helps iteration 0 of a rerun avoid the same state-machine
   mistake, that's a measurable win.
2. **Similar-shape tasks should be accelerated.** If a future parsing fixture
   (e.g. bug_008 sibling with different delimiter rules) can retrieve prior
   quoting-parser failures and reach a pass in fewer iterations, memory has
   paid for itself.

The ablation methodology for v0.3b will be a repeat-run protocol:
memory-empty vs memory-warm on the same fixture set, measuring pass rate,
iterations-to-pass, and tokens-to-pass.

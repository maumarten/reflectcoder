# v0.2 ablation — stub vs reflective

Both agents use the same model (`llama-3.3-70b-versatile`) and the same proposer
system prompt. The only difference is the control flow: `stub` makes one LLM
call and returns; `reflective` runs a plan → patch → test → reflect → retry
loop with `max_iter=3` and a circuit breaker.

## Headline

| Agent        | Fixtures | Pass | Pass rate | Total tokens | Wall clock |
|--------------|----------|------|-----------|--------------|------------|
| stub         | 5        | 4    | 80.0%     | 2721         | 6.3s       |
| reflective   | 5        | 5    | **100.0%**| 2960         | 6.5s       |

**Delta:** +1 fixture passed (bug_005_parse_query_string) at +9% token cost.

## Where the loop actually fired

In the published runs both agents solved their fixtures on the first attempt
when they passed. The reflective loop's retry-after-reflection behaviour was
only exercised during development, on a prior run where iteration 0 on
bug_004 produced a malformed JSON patch: the parser rejected it, the loop
generated a corrective reflection, and iteration 1 passed. That trace is
available in the git history under the earlier runs under `runs/`.

So: on this fixture set the reflective loop's pass-rate contribution comes
partly from iteration (observed) and partly from subtle decoder-level
differences between the two agents' request shapes (even when iter-0
succeeded, reflective's prompt included a short trailing instruction block
that appears to nudge the model toward more careful JSON on bug_005
specifically). We are not yet able to attribute the +1 cleanly to the loop
machinery alone on these fixtures.

## Honest interpretation

On canonical Python bugs, `llama-3.3-70b-versatile` has a high one-shot success
rate given a well-specified prompt. The reflective loop is therefore an
**insurance mechanism** here, not a primary contributor: it collects the long
tail of cases where the proposer produces malformed output, proposes a wrong
fix that a simple test reveals, or — as observed in dev — the LLM-level call
fails (e.g. Groq `json_validate_failed`). The circuit breaker and LLM-error
recovery in [`reflective.py`](../../src/reflectcoder/agents/reflective.py)
mean the loop degrades gracefully instead of crashing.

## What this tells us about v0.3

The fixture set is too easy to separate "loop" from "no loop" with signal.
v0.3 needs fixtures where one-shot is intractable, specifically:

- **Multi-file tasks** where the bug is in a file not obviously flagged by
  the problem statement, so the test failure is what points at the real fix.
- **Under-specified problems** where the expected behaviour is only pinned
  down by reading the test output.
- **Adversarial edge cases** layered on correct-looking code (e.g.
  locale-dependent parsing, unicode bytes boundaries).

Once the stub sits below ~60% on such a set, the reflective loop's value
becomes measurable, and v0.3's failure-memory layer can be evaluated on top
of that.
